## Триггеры

- Пользователь явно просит подготовить коммит: «подготовить коммит», «подготовь коммит», «оформи коммит», «prepare commit», «prepare a commit», «get the commit ready» и близкие по смыслу формулировки;
- Без явной просьбы пользователя скил не активируется;

## Принцип

- Скил не предписывает LLM выполнять коммиты, пуши, слияния, теги - эти действия всегда остаются за пользователем;
- Исключительный результат скилла - сформированные инструкции (план команд и платформенных шагов) в зависимости от ситуации и статуса репозитория;
- Все команды из плана выполняет пользователь лично;

## Разрешённые действия агента

Агенту разрешается самому применять предлагаемые изменения двух видов - но только если текущий git flow и его текущий статус этим действиям не противоречат:

1. Изменение файла версий: выставить предлагаемую будущую версию во 2-ю строку `.version` и выполнить `make version_update` (подстановка в целевые файлы + копирование 2-й строки в 1-ю);
2. Изменение чейнждлога: добавить предлагаемую секцию в `CHANGELOG.md` (версия, дата, типизированные строки);

Условия непротиворечия (все должны выполняться одновременно):

- Репозиторий настроен под git flow: маркер `.git_flow/.git-flow-*` присутствует и объявлен вариант 1. Без объявленного флоу репозиторий ещё не готов - правки запрещены, агент рекомендует их как шаги плана (включая `make git_flow_init`); при вариантах 2-5 версии и чейнджлог принадлежат seal-у и фрагментам - ручные правки противоречат флоу и запрещены (агент предлагает команды фрагментов);
- Предлагаемая версия - корректный semver, строго больше текущей 1-й строки `.version`;
- Секции с предлагаемой версией ещё нет в `CHANGELOG.md`;
- Нет несобранных фрагментов и незавершённой печати (статус по `make git_flow_status`);
- Рабочая ветка - main; на task/hotfix-ветках и gate-ветках файлы версий и чейнджлога агенту не принадлежат;

При любом нарушении условий агент только формулирует инструкции, а правки выполняет пользователь.

## Последовательность действий

1. Определить состояние репозитория (только чтение, без изменяющих команд):

  - Вариант флоу - по маркеру `.git_flow/.git-flow-*` в корне проекта;
  - Текущая ветка: main / task-* / hotfix-* / staging / release/*;
  - Грязное ли дерево (`git status --porcelain`);
  - Есть ли фрагменты чейнждлога (`.git_flow/changelog_fragments/`);
  - Незапушенные коммиты, открытые merge request-ы, соотношение тега и `.version`;
  - Разрешается запускать `make git_flow_status` и `make git_flow_help` - они безопасны (только чтение);

2. Проанализировать сделанные изменения и предложить записи чейнджлога:

  - Источники: `git status --porcelain`, `git diff` (и `git diff --staged`), незапушенные коммиты текущей ветки (`git log @{u}..HEAD --oneline` при наличии апстрима);
  - Понять смысл изменений, а не перечислить файлы: что нового умеет код, что исправлено, что удалено;
  - Предложить пользователю одну или несколько строк фрагментов в формате `<Type>: <one English line>` (типы: Added, Changed, Fixed, Deprecated, Removed, Security):

    - Каждая строка - на английском, максимально краткая, отражает суть изменения с точки зрения пользователя проекта, а не реализации;
    - Самое значимое изменение - первым: старшая строка станет заголовком MR и основой сообщения коммита;
    - Одно семантическое изменение - одна строка; механические шумы (форматирование, временные файлы) в фрагменты не попадают;

  - Если фрагмент на задачу уже существует - сверить с дифами: предложить дополнить (новая строка той же командой добавится в существующий фрагмент) или оставить как есть;
  - Готовые команды включить в план: `make git_flow_task_fragment "<Type>: <line>"` - пользователю остаётся вставить их;

3. Сформулировать план дальнейших действий по фазе, в которой находится репозиторий. План - это нумерованный список точных команд, которые пользователю остаётся ввести, плюс платформенные шаги (слияние MR). Пользователь выполняет команды сам!

  Возможные фазы и планы:

  - Флоу не объявлен: агент сам ничего не применяет; предложить `make git_flow_init <1..5>` (помочь выбрать вариант), после инициализации - план выбранного варианта; правки `.version` и `CHANGELOG.md` включить в план как шаги пользователя (готовый текст секции + выставление будущей версии, например по скиллу skill-makefile-version-update);

  - Вариант 1, изменения на main: `make git_flow_commit_push "<Type>: <message>"`; на вопрос `Tag now?` ответить y - версия, тег и пуш уйдут атомарно (тег = прод-релиз); сообщение коммита строится из старшей предложенной строки чейнджлога; при выполнении условий раздела «Разрешённые действия» агент сам выставляет будущую версию в `.version` и добавляет секцию в `CHANGELOG.md`;

  - На task-ветке с грязным деревом: сначала `make git_flow_commit "<Type>: <message>"`;
  - На task-ветке без фрагмента: `make git_flow_task_fragment "<Type>: <one English line>"` с предложенными на шаге 2 строками - фрагмент станет строкой в CHANGELOG и заголовком MR;
  - Далее по варианту:
    - Вариант 2: `make git_flow_task_finish` (сквош в main) → `make git_flow_seal`;
    - Вариант 3: `make git_flow_task_merge_develop` → `make git_flow_task_finish` → слить MR в main (squash) → `make git_flow_seal`;
    - Вариант 4: `make git_flow_task_merge_develop` → `make git_flow_task_finish` → слить MR в staging (squash) → `make git_flow_promote` → слить MR staging → main (squash) → `make git_flow_seal`;
    - Вариант 5: `make git_flow_task_merge_develop` → `make git_flow_task_finish` → слить MR в поезд release/x.y (squash) → `make git_flow_promote` → слить MR поезд → main (squash) → `make git_flow_seal` (штампует x.y.0 и бампает поезд);
  - На hotfix-ветке (варианты 4-5): фрагмент обязателен - `make git_flow_task_fragment "Fixed: <one English line>"` → `make git_flow_commit "Fixed: <message>"` → `make git_flow_hotfix_finish` → слить MR в main (squash) → `make git_flow_seal`;
  - Открытый MR ждёт слияния: слить (squash) на платформе → `make git_flow_seal`;
  - На main с несобранными фрагментами: `make git_flow_seal`;
  - На main, всё запечатано: сообщить, что продвигать нечего - тег на main соответствует `.version`;

4. Требования к плану:

  - Каждая команда - с путём (при работе в воркдериве задачи начинается с `cd ../<project>-task-<label>`, печать всегда из корня проекта);
  - Платформенные шаги (слияние MR) помечать явно: "руками на GitHub";
  - Указывать ожидаемое состояние после плана: тег vX.Y.Z на main, ветки синхронизированы, CHANGELOG собран из фрагментов (включая предложенные на шаге 2 строки);
  - Версию в сообщения коммитов не писать - её штампует seal автоматически;
  - CHANGELOG.md не редактировать при вариантах 2-5 - секцию собирает `make git_flow_seal` из фрагментов; при варианте 1 и без флоу действует раздел «Разрешённые действия»;

5. Перед завершением плана предложить пользователю отразить изменения в README.md, если он не менялся с прошлого коммита (дополняется на языке оригинала и едет теми же коммитами задачи); правки README вносит сам пользователь - либо агент, но только по отдельной явной просьбе пользователя, вне этого скилла;

6. Оценка ADR и runbook - по итогам анализа изменений (шаг 2) оценить их необходимость:

  - ADR (`docs/adr/[lang_code]/*`) - изменение несёт архитектурное решение:
    - новая зависимость или выбор технологии;
    - сдвиг границ сервисов или модели данных;
    - отклонённая альтернатива, которую стоит зафиксировать;
  - Runbook (`docs/runbooks/[lang_code]/*`) - вводится или меняется эксплуатационная процедура:
    - развёртывание, миграция, откат;
    - восстановление после инцидента;
  - Степень необходимости определяется так:
    - на усмотрение агента - предложить документ с однострочным обоснованием;
    - прямое указание пользователя - документ формулируется безусловно;
  - При достаточной необходимости сформулировать текст документа шагом плана:
    - следовать именованию, нумерации и формату существующих документов каталога;
    - язык - по существующим документам целевого каталога;
    - пустой или отсутствующий каталог - язык README проекта;
    - документ едет теми же коммитами задачи;
  - Правки файлов - по правилу README из шага 5: вносит пользователь или агент;
  - Прямое указание пользователя на документ - явная просьба агенту на правку;
  - При недостаточной необходимости кратко отметить в финале, что документов не требуется;

7. Финал: выдать план пользователю одной сводкой - от текущего состояния до тега на main. Команды запускает сам пользователь.
